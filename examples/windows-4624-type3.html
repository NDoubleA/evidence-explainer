    Proves vs does NOT prove

    ✔ This line proves

    • CONFIRMED A valid credential for CORP\j.okafor was accepted by FS01 (the claim of FS01's log).
    • CONFIRMED The connection came from 10.20.4.37, port 51544, at 14:32:07 UTC.
    • CONFIRMED It was a network logon (type 3), not someone at FS01's console.
    • CONFIRMED NTLM v2 was used, not Kerberos.
    • CONFIRMED A session 0x5A3F21C exists that you can follow.

    ✘ It does NOT prove

    • UNKNOWN That the person using j.okafor did it. Proving identity is not the same as proving the person (or that they were permitted to).
    • UNKNOWN How the credential was obtained: typed, cached single sign-on, phished, or a stolen hash replayed.
    • UNKNOWN Which program on 10.20.4.37 made the connection.
    • UNKNOWN What happened next: files read, shares touched, processes started (needs 5140/5145, 4688 or Sysmon 1, 4672).
    • UNVERIFIED That the machine is really named WS-0147: NTLM lets the client choose that name.
    • UNVERIFIED That the password was guessed. A 4624 is a success, not a brute-force signal by itself.

    Blind spot

    What this sensor could not see

    UNKNOWN FS01 sits at the destination. It only sees what arrived at its door: the credential, the source IP, the protocol. It can't see inside WS-0147 (who was logged on there, what process opened port 445, whether a hash was pulled from memory) or inside the session unless extra auditing is on.

    Which logs fill the gap
    • Source host: Sysmon Event 3 (network connection → which process hit 10.20.1.15:445), 4648 (explicit credentials used), EDR process tree.
    • DC01: 4776 (the DC validated an NTLM credential for j.okafor, with the workstation name), plus 4625/4771 failures before it.
    • FS01 after logon: 4672 (special privileges = admin), 5140/5145 (share/file accessed, needs Object Access auditing), 4688 or Sysmon 1 (process created), 4634 (logoff, gives session length).
    • Network: Zeek smb_mapping.log / ntlm.log or firewall logs for the same 10.20.4.37:51544 → :445 flow.

    Triage decision tree · follow the paths

    Step through the yes/no questions below by checking each named source. Branches collapse and expand to guide triage.

    Next pivot

    1. Follow the session on FS01. Pull every event carrying 0x5A3F21C: 4672 (was it admin?), 5140/5145 (which shares/files), 4688 (did anything run?), 4634 (when did it end?).
    2. Widen on the source. Did 10.20.4.37 do NTLM type-3 logons to other servers in the same 10 minutes? One server = normal work. Many = possible lateral movement.
    3. Go to the source host. Look up 10.20.4.37 in DHCP/asset inventory, then that host's Sysmon 3 / EDR for the process that connected to 10.20.1.15:445, and the DC's 4776 for the same minute.
    KQL example
    // Microsoft Sentinel · SecurityEvent (example values)
// 1) Everything in this logon session on FS01
SecurityEvent
| where TimeGenerated between (datetime(2026-10-21 14:30) .. datetime(2026-10-21 16:30))
| where Computer == "FS01.corp.example.local"
| where TargetLogonId =~ "0x5a3f21c" or SubjectLogonId =~ "0x5a3f21c"
| project TimeGenerated, EventID, Activity, ShareName, NewProcessName, PrivilegeList
| order by TimeGenerated asc

// 2) Fan-out from the same source IP
SecurityEvent
| where TimeGenerated between (datetime(2026-10-21 14:20) .. datetime(2026-10-21 14:45))
| where EventID == 4624 and LogonType == 3 and AuthenticationPackageName == "NTLM"
| where IpAddress == "10.20.4.37"
| summarize Hosts = dcount(Computer), HostList = make_set(Computer), Accounts = make_set(TargetUserName)
